Architecture & User Manual

A guide to the internal workings and operational use cases of the BSP Kafka GC Analyzer.

System Overview

The BSP Kafka GC Analyzer is a self-hosted diagnostic web application for JVM garbage collection and host resource evidence across Kafka deployments. It retrieves configured logs, calculates statistics, and flags observed pressure or unusual patterns for investigation. Missing or stale evidence cannot establish current health, and a pattern is not proof of a memory leak or Kafka service impact.

GC logs reveal stop-the-world pauses, GC throughput, heap occupancy, and allocation behavior; SAR adds CPU, memory, disk, and network observations. Their association helps prioritize investigation, but Kafka workload, latency, replication health, and partition placement must be checked before prescribing scaling or configuration changes.

Application Control

Use manage-app.sh for setup, deployment, startup, shutdown, status, and logs. Normal startup uses installed dependencies without contacting package repositories or adding demo data. Setup/deploy installs dependencies; seed is an explicit demo-only operation. Startup waits for a successful /api/health response.

Ingestion Pipeline Architecture

Scheduled collection reads configured hosts and persists fleet history. GC uses consumed byte offsets; SAR uses timestamp-keyed sample identity and fixed 60-second rollups. One-time investigations are a separate bounded, in-memory path with no database writes.

Scraping Modes

The collection layer supports two scraper paradigms configured per-node:

  • Local Scraper (source: local): Reads log files locally on disk. Uses file seeks and offsets mapped to file paths to read only newly appended log data.
  • SSH Scraper (source: ssh): Connects remotely via Paramiko SSH. To optimize network load and memory consumption, the collector queries remote files' inodes and sizes using: 
    stat -c '%i %s' '/path/to/log' 2>/dev/null || stat -f '%i %z' '/path/to/log'
    If the remote file's inode matches the recorded state and its size is greater than or equal to the previous offset, the analyzer executes: 
    tail -c +[OFFSET] '/path/to/log'
    This fetches the delta since the last consumed offset, subject to command timeouts and output bounds. Inode/size checks handle rotation or truncation; a failed read must not consume its offset.

Metrics and consumed offsets commit transactionally. Incomplete trailing GC records remain retryable on a later pass. Complete malformed records are reported as skipped with limited quality, not converted into valid observations. Missing or malformed-only evidence is unknown, not a refreshed healthy observation; durable malformed-record quarantine is pending. Uptime-only GC records stay relative unless a verified JVM start anchor establishes absolute time. File dates and collection time are not invented as event timestamps.

Storage Layer

The system uses embedded SQLite (gc_history.db or gc_live.db) for instance inventory, GC metrics, normalized SAR samples, fixed-minute host rollups, and collector states. Host data remains linked to each JVM instance; there is no separate host-topology redesign.

GC and host rows share instance identity and a UTC basis, but are rebucketed to an hourly grid for correlation.
sar_samples (instance_id, ts) sample_json One sparse normalized observation per timestamp, not repeated full-report blobs. Repeated/late samples are idempotent; corrections and complementary fields merge, then only affected rollups are recomputed.

Missing measurements remain null through parsing, storage, charts, and analysis. Additive migrations preserve legacy rows, but old parser-defaulted zeroes and peaks already averaged away cannot be recovered without reimporting source reports. No migration guesses which old zeroes were real observations.

Query Aggregation

Preserve Counts, Duration, Peaks, and Missing Values

GC daily trends use SQLite grouping. SAR trend/range queries combine stored per-metric weights and peaks in Python, using duration weights when known and sample weights otherwise. Empty measurement lists remain unavailable, not zero. Only query-boundary SAR buckets need sample-level rereads to exclude observations outside an explicit time range. 

SELECT (ts / 86400) * 86400 AS day, AVG(heap_used_mb) AS heap_used_avg, MAX(heap_used_mb) ... GROUP BY day

Codebase Component Breakdown

The Python packages and web resources are organized logically as follows:

1. Server & API Controller (gcanalyzer/app.py)

An asynchronous FastAPI application hosting API endpoints. It runs an event-loop background task that executes cluster scheduler ticks, handles authentication via the `gc_session` cookie, and exposes JSON APIs for topology, snapshots, trends, and job history.

2. Scraper Task Scheduler (gcanalyzer/scheduler.py)

Uses a thread pool executor to concurrently query remote or local nodes. It feeds log text to the parser and writes offsets and resulting statistics back to the database in a sequential transaction block. The concurrency limit is read from `config.json`.

3. Log Collector (gcanalyzer/collector.py)

Hosts Paramiko SSH client connections and local filesystem access functions. Contains the logic for the remote delta-syncing strategy (utilizing remote tailing) and maps default Kafka GC log globs based on node roles (broker, controller, history, zookeeper).

4. Log Parser (gcanalyzer/parser.py)

Parses unified and legacy GC records, including pause-only observations, heap transitions, collector identity, and event time. Absolute timestamps require source evidence or a verified JVM start anchor; uptime-only logs stay relative. Missing heap or rate evidence can limit health grading without erasing observed pauses.

5. Fleet Health Analyzer (gcanalyzer/analyzer.py)

Scores usable GC evidence on the A-F scale using throughput, pause, Full GC, and heap-pressure thresholds. Inadequate evidence returns ? / unknown with a null score. Findings explain observed risks and investigation steps; they do not prove Kafka service impact or justify a configuration change by themselves.

The grade is a deterministic report-card summary of the node's GC risk: A = healthy, B = good, C = watch, D = at risk, and F = critical. The score starts at 100 and subtracts risk points for low throughput, long stop-the-world pauses, Full GCs, and high post-GC heap pressure.

6. SAR Collector & Parser (gcanalyzer/collector.py, sar_parser.py)

In an independent pass using the configured SSH access, runs TZ=UTC LC_ALL=C sadf -j -- -A and falls back to TZ=UTC LC_ALL=C sar -A when JSON is unavailable. Both formats normalize into SarSample, preserving null missing fields. Text AM/PM times and ISO or slash-format dates are supported. A report's timezone converts host observations to UTC; only GC events with verified absolute time can be aligned with them.

7. Host Health Analyzer (gcanalyzer/sar_analyzer.py)

Aggregates CPU busy/iowait, memory/swap, disk util/await, and NIC observations. Complete usable evidence receives an A–F host grade. Missing evidence is unknown; partial evidence has grade ?, status partial, and a null score, while observed pressure can still be reported. Unobserved resources are not described as healthy zero-activity resources.

8. Correlation Engine (gcanalyzer/correlate.py)

Re-buckets overlapping GC and host evidence per instance to hourly observations, then computes Pearson correlation and GC-storm co-occurrence where each metric pair has usable values. It distinguishes gc_bound, host_bound, mixed, healthy, and insufficient_data. Missing values are not zero-filled. Association is not causality, and lack of correlation does not prove a JVM-only cause.

9. Scaling Advisor (gcanalyzer/scaling_advisor.py)

Identifies observed broker pressure and cross-node skew in CPU busy and network egress, with source-quality gates. Pressure leads to investigate, not a prescription for more brokers, larger heaps, or partition movement. Uniform pressure and isolated hot brokers need different follow-up evidence, but neither establishes a scaling direction without Kafka workload, latency, replication, and partition-placement observations.

10. ML Tech Preview (gcanalyzer/ml_insights.py)

Dependency-free robust z-score (median/MAD) scoring needs at least 10 observed baseline hours per feature and usable recent evidence. Noise floors limit flat-baseline false alarms. Optional IsolationForest requires scikit-learn and sufficient complete feature vectors; it is fitted request-local only, with no persistent model or continuous learning. Output identifies actual method use, readiness, and unavailable/error states. Deterministic rules remain the source of truth for grades; anomaly scores are advisory, not diagnoses.

11. Capacity Forecast (gcanalyzer/forecast.py)

Each signal requires at least 14 observed days, 80% calendar coverage from its first observation through the query date, no gap greater than two days between observed days, five observed days in the last seven, and a latest observation within 24 hours. Missing, stale, or partial source quality can block predictions sooner; source freshness defaults to two hours.

Theil-Sen supplies a robust linear projection, not a validated Kafka capacity model. There is no seasonality model, backtesting, or calibrated uncertainty. Confidence is low or medium, never high; future breach dates require medium confidence and a consistent rising trend. Cluster risks lead to investigate with caveats, not scaling prescriptions.

Server Health (SAR), Correlation & Scaling Advisor

The analyzer collects host activity via sysstat (sar/sadf) and compares it with GC pressure where timestamps overlap. At cluster level it highlights resource pressure or peer skew to investigate. Kafka-native evidence is required before selecting capacity, heap, or partition-placement changes.

Prerequisite

Each host needs sysstat installed and its collection cron enabled (usually on by default):

sudo apt-get install -y sysstat   # Debian/Ubuntu
sudo systemctl enable --now sysstat

sudo yum install -y sysstat       # RHEL/CentOS/Amazon Linux
sudo systemctl enable --now sysstat

No analyzer agent is deployed on the host. SAR uses configured host access in a separate collection pass; sysstat must already be recording the required observations.

Configuration

Add a sar: block to a cluster's node defaults (opt-out, not opt-in):

defaults:
  sar:
    enabled: true
    # source: ssh        # defaults to the node's own `source`
    # sar_bin: sar
    # sadf_bin: sadf

Independent Collection, Independent Failure

SAR collection runs as its own pass, separate from GC collection. A SAR failure does not invalidate usable GC evidence, or vice versa. The dashboard shows each source's fresh/partial/stale/missing state. Retained historical rows do not establish current healthy status; a daily SAR upload alone does not maintain freshness under the two-hour default.

Onboarding Clusters

New Kafka environments are registered with the application by submitting a configuration file in YAML format. The system supports full customization of authentication credentials and log paths.

YAML Configuration Schema

Below is a fully populated template schema detailing all available options:

cluster: demo-prod-cluster     # Unique identifier

env: PROD                      # Environment tier (PROD, UAT, etc.)

defaults:
  source: ssh                  # ssh | local
  port: 22
  user: kafka-admin
  key_path: ~/.ssh/id_rsa      # Private key path
  kafka_home: /opt/kafka       # Resolves default log directory
  # password: secret           # Or fallback password if key is not used

nodes:
  - id: broker-1
    role: broker
    host: 10.0.1.10
  - id: broker-2
    role: broker
    host: 10.0.1.11
  - id: controller-1
    role: controller
    host: 10.0.1.20
    # Override paths explicitly if defaults don't fit
    log_paths:
      - /var/log/kafka/gc-server.log*

    role: zookeeper
    source: local
    local_paths:
      - ./samples/zookeeper-1-gc.log
Name Duplicate Validation

To prevent accidentally overwriting configurations, onboarding a new cluster whose name matches an already existing cluster YAML file returns an API 400 Bad Request error. If you wish to update a cluster, edit the configuration in the Settings panel directly.

Dashboard Reference

The UI operates as a Single-Page Application (SPA) providing multi-tier navigation views.

Navigation Trees

The sidebar renders a structured topology: Region → Environment → Cluster → Component Group → JVM Instance. Clicking a tier displays a corresponding context panel:

  • Fleet View: Displays a grid of all registered clusters showing aggregated health and active alert counts.
  • Cluster Overview: Shows total aggregate memory usage, JVM version configurations, active telemetry (e.g. worst pause time in 24h), and a targeted "Needs Attention" watch list highlighting degraded nodes.

Data Quality and Diagnostic Summary

? = unknown: missing or stale data cannot establish current health. Missing CPU, memory, disk, or GC values are shown as unavailable, not zero. Source freshness and coverage appear separately from the grade. Historical evidence may still be available when current health is unknown.

A GC collection containing only malformed or unsupported complete records also marks current health unknown. Confirmed recent GC alerts remain visible; a later usable collection can restore current health. Collection quality is stored separately from observed metrics.

Snapshot quality contains state, last_observed_at, age_seconds, available_metrics, and missing_metrics. GC snapshots retain instance, latest, metrics, health, alerts, and findings; host snapshots omit alerts. Missing/stale sources return empty current metrics/advice and health {grade: "?", status: "unknown", score: null}, while latest can expose retained historical values. Freshness defaults to two hours via GC_SOURCE_MAX_AGE_S and SAR_SOURCE_MAX_AGE_S.

Results use Analysis complete, followed by What we found, Why it matters, and Next step. GC and host events occurring together suggest a possible contributor, not a confirmed cause. Kafka service impact remains unconfirmed until Kafka metrics are connected.

Analyze Logs: One-Time Investigations

Open Analyze logs to upload GC text or gzip files. Files are separate investigations unless you select Files are rotations from the same JVM. Never group logs from different JVMs. Optional SAR JSON/text must come from the same host; comparison accepts one JVM group at a time.

Uptime-only GC logs stay relative. Supply a verified JVM start time with timezone, such as 2026-09-12T00:00:00Z, to establish UTC; the parser never invents a date. Export SAR using TZ=UTC LC_ALL=C sadf -j -- -A; binary SAR files must be exported first. Optional report_date anchors SAR text, not JVM uptime. The editable report_timezone defaults to UTC; choose the report's IANA timezone, such as America/Toronto, for local exports. Embedded SAR JSON UTC/offset information takes precedence, and ambiguous/nonexistent daylight-saving wall times are rejected. Only overlapping observed timestamps are compared; gaps are not zero-filled.

Call POST /api/investigations/analyze as either an authenticated admin or read-only user. Limits are 12 GC files, 4 MiB expanded per file, 8 MiB expanded total including SAR, a 12 MiB request body, and two concurrent investigations per process. Analysis runs in memory with no database writes; fleet history and learning baselines are untouched. This differs from the admin-only persistent SAR upload endpoint. Download report produces a standalone HTML summary.

Prometheus Settings

As an admin, open Settings → Prometheus. Enter the server base URL, choose Save settings, then Test connection. HTTP and HTTPS with no authentication are supported. Test connection uses the saved address only; save any edits first. A successful test confirms query API access, not Kafka metric availability. The result is the last test, not continuous monitoring, and is cleared when the app restarts.

The screen shows the full path to prometheus.json, stored at the project root by default and excluded from Git. To move it, set GC_PROMETHEUS_CONFIG=/etc/gcanalyzer/prometheus.json and restart the app. The parent directory must exist and be writable by the app user. Saved files use 0600 permissions. Direct JSON edits take effect when Settings is reloaded; the app need not restart for content changes. The generic schema is in prometheus.example.json.

Selection fields preserve raw job, region, tier, infra, az, service, and full instance values, including exporter ports. Empty lists have no selection restriction. Tiers include DEV, UAT, PROD, sandbox, and stage. Infrastructure includes icp and phy. Service aliases map Kafka to broker and registry to schema-registry. The expected scrape interval is 60 seconds.

Settings and connection testing are available; metric ingestion is not yet enabled. Saved filters and service aliases are reserved for that integration. This app does not change the external prometheus.yml or its scraping interval. Admin-only APIs: GET/PUT /api/settings/prometheus and POST /api/settings/prometheus/test.

The Excel mapping can be added later for cluster-specific analysis. A job named bvp-region-env can contain multiple Kafka clusters and is not itself a cluster identity. Cross-region ZooKeeper tiebreakers are intentional: preserve their actual region and verified logical cluster membership. A region differing from the job name is not, by itself, an error. Keep environment baselines distinct and never infer cluster membership solely from job, region, or AZ.

Capacity guidance and forecasts remain advisory. Missing, stale, or sparse evidence withholds predictions or reduces confidence. Confirm Kafka workload, replication health, latency, and partition placement before changing capacity.

Alerting & Diagnostic Logic

The analyzer evaluates statistics from the last hour of records to identify operational issues.

Alert Categories

Alert Type Severity Trigger Metric Condition Implication
Full GC Critical full_gc_count > 0 A Full stop-the-world GC was observed. Check its cause and surrounding heap evidence; this alone does not prove heap exhaustion.
Long Pause Critical pause_max_ms > 500ms An observed STW pause exceeded the threshold. Compare Kafka latency, timeouts, and replication health to establish service impact.
Heap Pressure Warning heap_after_pct > 85% The observed post-GC live set has limited heap headroom. Investigate trends and allocation demand; this is not an OOM prediction.
GC Storm Warning time_in_gc_pct > max(5%, 3x baseline) The observed fraction of time in GC exceeds its threshold. This is not a direct host CPU-utilization measurement.
GC Frequency Warning gc_per_min > max(20, 2x baseline) GC cycles are unusually frequent. Check allocation behavior and application latency before attributing Kafka throughput loss.

Administration & Troubleshooting

The backend serves static files and handles scheduler tasks in the background. Use manage-app.sh status 8083, manage-app.sh logs 8083, and manage-app.sh stop 8083 for routine process control before dropping down to module-level commands.

Managing Concurrency

If the analyzer is scraping hundreds of hosts, adjust the maximum parallel scraping worker limit in the root `config.json` file: 

{
  "concurrency": 25
}

Scraping Job Logs Pop-up

Clicking **"View Logs"** in the jobs sidebar opens an asynchronous log modal. You can inspect connection attempts, files found, read byte sizes, parsing stats, and errors (such as SSH timeout or permission denials) in real-time.

Running Scrapes Manually

You can force a single scraping pass to run outside of the FastAPI runtime. Execute the following command from the project root directory: 

.venv/bin/python -m gcanalyzer.scheduler --db gc_live.db --once

Verification Coverage

Use explicit demo mode for seeded-history tests; live-clock tests disable it and explicit fixed-now cases remain deterministic. The suite covers GC relative time and retryable offsets, SAR nulls and AM/PM/timezones, fixed-grid late/repeated/corrected samples, transactional rollback, weighted rollups, migrations, stale snapshots, and nullable queries.

Advice tests distinguish healthy/unknown/pressure states and assert investigate rather than unsupported scaling prescriptions. Forecast tests check calendar coverage and withheld projections; ML tests check per-feature baseline readiness and actual model status. Investigation tests cover authorization, upload limits, timestamp alignment, and no history writes. Static checks protect theme behavior, health-grade legends, escaping, and control commands.

GC_DEMO_MODE=1 .venv/bin/python -m pytest -q
